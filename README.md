# MiniDbg

Навчальний консольний дебагер на C для Windows x64. Запускає вибрану користувачем програму `.exe` та керує її виконанням через Windows Debug API.

MiniDbg дозволяє встановлювати повторювані точки зупинки, виконувати окремі машинні інструкції, переглядати регістри процесора та пам’ять.

**Дебагер підтримує запуск власних native Windows x64-програм за ім’ям або шляхом.** `demo.exe` — готовий приклад для демонстрації. Для запуску іншого сумісного `.exe` не потрібно змінювати його вихідний код або перебудовувати MiniDbg.

## Мета проєкту

Дослідити роботу дебагерів на практиці:

- запуск процесу під налагодженням;
- обробку подій Windows Debug API;
- програмні точки зупинки через INT3;
- покрокове виконання через Trap Flag;
- читання регістрів і пам’яті процесу;
- обробку винятків і завершення процесу.

Дебагер реалізовано без GDB, емулятора процесора та стороннього рушія налагодження.

## Вимоги

Для запуску:

- Windows 10/11 x64;
- зібраний `bin/minidbg.exe`;
- native Windows x64-програма для налагодження.

Для збірки:

- GCC x64 із MSYS2 UCRT64, доступний у `PATH`;
- PowerShell.

Python 3.9+ потрібен лише для інтеграційних тестів. Для запуску готового дебагера Python і компілятор не потрібні.

Скрипт також передбачає збірку MSVC з відповідного x64 середовища Visual Studio, якщо GCC недоступний. Перевірку цієї гілки для поточної версії не підтверджено.

## Збірка

Відкрийте PowerShell у корені проєкту:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

Після успішної збірки будуть доступні:

```text
bin/minidbg.exe
bin/demo.exe
bin/test_commands.exe
```

Параметр `ExecutionPolicy Bypass` діє лише для цього запуску PowerShell і не змінює постійні налаштування системи.

Каталог `bin/` виключено з Git через `.gitignore`, тому після клонування репозиторію проєкт потрібно зібрати.

Після змін вихідного коду необхідно повторно виконати збірку.

## Запуск власної програми

### Інтерактивний вибір

Відкрийте `run.cmd` або виконайте:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\run.ps1
```

Також можна безпосередньо запустити:

```powershell
.\bin\minidbg.exe
```

У запрошенні `Program>` введіть шлях до потрібної програми:

```text
Program> C:\Projects\My App\app.exe
```

Підтримуються пробіли та кирилиця в шляху. При інтерактивному вводі лапки навколо шляху необов’язкові; шлях у лапках також приймається.

Якщо програма доступна в поточному каталозі, поруч із дебагером або в `PATH`, достатньо короткого імені:

```text
Program> app.exe
```

Розширення `.exe` можна не писати.

Порядок пошуку короткого імені:

1. Поточний каталог.
2. Каталог `minidbg.exe`.
3. Каталоги зі змінної середовища `PATH`.

Дебагер не сканує весь диск. Для програми в іншій папці вкажіть повний шлях. Явно вказаний відсутній шлях не підміняється однойменним файлом із каталогу дебагера або `PATH`.

Перед запуском MiniDbg показує знайдений шлях у рядку `Target:`. Після невірного імені або непідтримуваного файла можна повторити ввід.

Після завершення інтерактивного сеансу можна обрати іншу програму без перезапуску MiniDbg. Одночасно налагоджується один процес.

Команда `quit` на екрані `Program>` закриває MiniDbg без запуску нової програми.

### Запуск через аргумент командного рядка

З кореня проєкту:

```powershell
.\bin\minidbg.exe "C:\Projects\My App\app.exe"
```

У цьому режимі виконується один сеанс, після якого MiniDbg закривається.

Аргументи цільовій програмі не передаються. Вона успадковує поточний робочий каталог; це потрібно враховувати, якщо програма використовує відносні шляхи до ресурсів.

## Команди

| Команда | Призначення |
| --- | --- |
| `break <address>` | Встановити повторювану точку зупинки на початку машинної інструкції. |
| `continue` | Продовжити виконання до наступної зупинки або завершення. |
| `step` | Виконати одну машинну інструкцію поточного потоку. |
| `regs` | Показати регістри x64, EFLAGS та зміни від попереднього перегляду. |
| `mem <address> <length>` | Показати 1–256 байт пам’яті у форматі hex + ASCII. |
| `quit` | Завершити цільовий процес із кодом 1 і закрити сеанс. |

Команди вводяться малими літерами. Порожній рядок залишає програму на паузі. Список команд виводиться при запуску та після помилки вводу; окремої команди `help` немає.

Адреси — шістнадцяткові: `401136` та `0x401136` означають те саме. Довжина для `mem` — десяткова.

### Псевдоніми адрес

У командах `break` і `mem` підтримуються:

| Запис | Значення |
| --- | --- |
| `0x140001000` або `140001000` | Абсолютна шістнадцяткова адреса. |
| `entry` | Точка входу виконуваного файла в поточному сеансі. |
| `base+1000` | База образу плюс шістнадцяткове зміщення `1000`. |
| `rip`, `rsp`, `rbp`, `rax`, … `r15` | Значення відповідного регістра поточного потоку. |

Приклади:

```text
break entry
mem rip 16
mem rsp 32
```

Псевдоніми обчислюються для поточного сеансу. Через ASLR абсолютні адреси можуть змінюватися між запусками.

## Перший сеанс із власною програмою

На початку MiniDbg зупиняється на системній точці завантажувача.

Введіть команди по черзі:

```text
break entry
continue
regs
mem rip 16
step
regs
```

Це дозволить зупинитися на вході програми, переглянути стан процесора та виконати одну інструкцію.

`Entry point` не обов’язково є функцією `main`: зазвичай це початок коду запуску runtime.

`step` виконує машинну інструкцію, а не рядок C. Після кроку MiniDbg показує попередній і новий RIP та, якщо читання доступне, наступні 8 байт коду. Ці байти не є дизасемблюванням.

Для точки всередині програми потрібна актуальна адреса початку інструкції. Автоматичне визначення функцій і рядків вихідного коду не реалізовано.

## Перегляд стану процесу

### Регістри

Команда `regs` показує регістри x64 та EFLAGS.

Перший виклик створює початковий знімок для поточного потоку. Наступні виклики порівнюються з попереднім знімком цього самого потоку; змінені значення позначаються `*`.

### Пам’ять

Команда `mem` показує адреси, шістнадцяткові байти та ASCII-подання.

Недоступні байти позначаються `??`. Якщо весь запитаний діапазон недоступний, виводиться повідомлення про помилку. Guard-сторінки пропускаються без зміни їхнього захисту.

У пам’яті встановленої точки зупинки видно байт `CC`. Під час зупинки на цій точці видно відновлений початковий байт.

### Винятки та завершення

Для звичайних винятків MiniDbg показує код, адресу, потік і позначку `first chance` або `second chance`.

`first chance` означає, що обробники програми ще можуть обробити виняток. Команда `continue` передає його цільовій програмі. Якщо виняток не оброблено, з’являється `second chance`; подальше продовження зазвичай призводить до завершення процесу.

На таких зупинках доступний перегляд регістрів і пам’яті, але `step` вимкнено.

Після завершення показуються код виходу цільової програми та статистика сеансу. Внутрішні кроки відновлення точок зупинки не враховуються як користувацькі кроки.

## Демонстраційна програма

З кореня проєкту виконайте:

```powershell
.\bin\minidbg.exe .\bin\demo.exe
```

Сценарій демонстрації:

1. На початковій системній зупинці введіть `continue`.
2. Демо надрукує адреси `checkpoint` і `total`, а також готові команди `break` і `mem`.
3. Скопіюйте надруковану команду `break` у MiniDbg.
4. Введіть `continue`. Очікується повідомлення `Hit breakpoint 1`.
5. Виконайте `regs` і команду `mem` із демо.
6. Виконайте `step`, потім `regs`, щоб побачити зміну RIP.
7. Продовжуйте виконання через `continue`, переглядаючи `total` між повторними зупинками.

Перед трьома викликами `checkpoint` значення `total` становитиме 0, 1 і 3. Після завершення програма виведе:

```text
total = 6
```

Дебагер повідомить про завершення процесу з кодом 0.

Власний INT3 у демо потрібен для зручного показу адрес. Інші сумісні програми можуть запускатися без додавання INT3 до їхнього коду.

## Архітектура

| Файл | Відповідальність |
| --- | --- |
| `src/main.c` | Запуск процесу, цикл подій, потоки, винятки та Trap Flag. |
| `src/debugger.c` | Точки зупинки, читання пам’яті та запис байта інструкції. |
| `src/commands.c` | Розбір команд, перевірка аргументів і адресні псевдоніми. |
| `src/target.c` | Вибір програми, пошук файла та Unicode-шляхи. |
| `src/inspect.c` | Вивід регістрів і пам’яті. |
| `src/console.c` | Оформлення консолі та статистика сеансу. |
| `src/debugger.h` | Спільні структури, константи та інтерфейси модулів. |
| `examples/demo.c` | Демонстрація повторних точок зупинки та зміни даних. |
| `tests/` | Модульні тести, інтеграційні сценарії та тестові програми. |

### Принцип роботи

1. `CreateProcessW` із прапором `DEBUG_ONLY_THIS_PROCESS` запускає вибрану програму під налагодженням.
2. `WaitForDebugEvent` отримує події процесу.
3. Для точки зупинки MiniDbg зберігає початковий байт інструкції та записує `0xCC`.
4. Під час влучання початковий байт відновлюється, а RIP повертається на адресу інструкції.
5. Trap Flag забезпечує виконання однієї інструкції.
6. Після внутрішнього кроку точка зупинки встановлюється повторно.
7. `GetThreadContext` і `ReadProcessMemory` використовуються для перегляду стану.
8. `ContinueDebugEvent` продовжує обробку подій і виконання процесу.

Після запису байта відновлюється початковий захист сторінки та викликається `FlushInstructionCache`.

Під час покрокового виконання інші потоки тимчасово призупиняються, щоб не пропустити зняту точку зупинки.

## Тестування

Для збірки та запуску всіх тестів:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test
```

Для вибору інтерпретатора:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test -Python "C:\Path\python.exe"
```

До проєкту входять:

- модульні C-тести розбору команд;
- модульні C-тести доступу до пам’яті та роботи з байтами точок зупинки;
- 22 інтеграційні тести дебагера;
- 11 тестів вибору програми.

Перевіряються повторні й сусідні точки зупинки, відновлення RIP, кроки, регістри, пам’ять, захист сторінок, потоки, винятки, завершення, помилковий ввід, Unicode та порядок пошуку файлів. Багатопотоковий сценарій усередині набору повторюється 20 разів.

Перевірено на Windows x64: збірка, модульні тести розбору команд і доступу до пам’яті та всі 33 інтеграційні тести пройдені.

Два повідомлення `Windows error 998` під час тестів пам’яті очікувані: перевіряється відмова запису в guard-сторінку та за недоступною адресою.

Після змін вихідного коду тестування потрібно виконати повторно.

## Обмеження

- Підтримуються native Windows x64-програми. Підтримка x86 та ARM64 не реалізована.
- Один цільовий процес; до 16 точок зупинки та до 64 відстежуваних потоків.
- Немає attach до вже запущеного процесу, налагодження дочірніх процесів і передачі аргументів цілі.
- Немає PDB, локальних змінних, прив’язки до рядків вихідного коду та дизасемблера.
- Адресу початку інструкції для точки зупинки обирає користувач.
- Видалення точок зупинки й апаратні точки не реалізовані.
- Крок через очікування іншого призупиненого потоку або блокувальний виклик може спричинити зависання.
- Недоступні та guard-сторінки не розблоковуються для перегляду.
- `quit` на зупинці та кінець вводу завершують ціль із кодом 1.
- Налагодження захищених системних процесів не передбачено.
