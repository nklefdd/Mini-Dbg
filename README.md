# MiniDbg

Навчальний консольний дебагер на C для Windows x64. Запускає вибрану користувачем програму `.exe` та керує її виконанням через Windows Debug API.

MiniDbg дозволяє встановлювати точки зупинки, виконувати окремі машинні інструкції, переглядати регістри процесора та пам’ять.

**Дебагер підтримує запуск власних native Windows x64-програм за ім’ям або шляхом.** `demo.exe` — готовий приклад для демонстрації можливостей. Для запуску іншого сумісного `.exe` не потрібно змінювати його вихідний код або перебудовувати MiniDbg.

## Мета проєкту

Дослідити роботу дебагерів на практиці:

- запуск процесу під налагодженням;
- обробку подій Windows Debug API;
- програмні точки зупинки через INT3;
- покрокове виконання через Trap Flag;
- читання регістрів і пам’яті процесу.

Дебагер реалізовано без GDB, емулятора процесора та стороннього рушія налагодження.

## Вимоги

Для запуску:

- Windows 10/11 x64;
- зібраний `bin/minidbg.exe`;
- native Windows x64-програма для налагодження.

Для збірки:

- GCC x64 із MSYS2 UCRT64, доступний у `PATH`;
- PowerShell.

Python 3.9+ потрібен лише для інтеграційних тестів. Для запуску готового дебагера Python і компілятор не потрібні.

У скрипті також передбачена збірка MSVC, але її перевірку для поточної версії не підтверджено.

## Збірка

Відкрийте PowerShell у корені проєкту:

```powershell
.\build.ps1 (powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 -Test)
```

Після успішної збірки дебагер і приклад будуть доступні в каталозі `bin`.

Каталог `bin/` виключено з Git через `.gitignore`, тому після клонування репозиторію проєкт потрібно зібрати.

## Запуск власної програми

### Інтерактивний вибір

Відкрийте `run.cmd` або виконайте:

```powershell
.\run.ps1
```

У запрошенні `Program>` введіть шлях до потрібної програми:

```text
Program> C:\Projects\My App\app.exe
```

Підтримуються пробіли та кирилиця в шляху. При інтерактивному вводі лапки навколо шляху необов’язкові.

Якщо програма доступна в поточному каталозі, поруч із дебагером або в `PATH`, достатньо короткого імені:

```text
Program> app.exe
```

Розширення `.exe` можна не писати.

Порядок пошуку:

1. Поточний каталог.
2. Каталог `minidbg.exe`.
3. Каталоги зі змінної середовища `PATH`.

Дебагер не сканує весь диск. Для програми в іншій папці вкажіть повний шлях.

Перед запуском MiniDbg показує знайдений шлях у рядку `Target:`. Після невірного вводу можна спробувати ще раз.

Після завершення інтерактивного сеансу можна обрати іншу програму без перезапуску MiniDbg. Одночасно налагоджується один процес.

Команда `quit` на екрані вибору закриває MiniDbg.

### Запуск через аргумент командного рядка

```powershell
.\bin\minidbg.exe "C:\Projects\My App\app.exe"
```

У цьому режимі виконується один сеанс, після якого MiniDbg закривається.

Аргументи цільовій програмі не передаються. Вона успадковує поточний робочий каталог; це потрібно враховувати, якщо програма використовує відносні шляхи до ресурсів.

## Команди

| Команда | Призначення |
| --- | --- |
| `break <address>` | Встановити повторювану точку зупинки. |
| `continue` | Продовжити виконання до наступної зупинки або завершення. |
| `step` | Виконати одну машинну інструкцію поточного потоку. |
| `regs` | Показати регістри x64, EFLAGS та зміни від попереднього перегляду. |
| `mem <address> <length>` | Показати 1–256 байт пам’яті у форматі hex + ASCII. |
| `quit` | Завершити цільовий процес із кодом 1 і закрити сеанс. |

Команди вводяться малими літерами. Порожній рядок залишає програму на паузі.

Адреси — шістнадцяткові: `401136` та `0x401136` означають те саме. Довжина для `mem` — десяткова.

### Псевдоніми адрес

Актуальні вихідні файли підтримують такі адреси в командах `break` і `mem`:

| Запис | Значення |
| --- | --- |
| `entry` | Точка входу виконуваного файла. |
| `base+1000` | База образу плюс шістнадцяткове зміщення. |
| `rip`, `rsp`, `rbp`, `rax`, … `r15` | Значення відповідного регістра поточного потоку. |

Приклади:

```text
break entry
mem rip 16
mem rsp 32
```

Готові EXE з початкового архіву можуть відставати від вихідного коду. Для використання актуальних можливостей спочатку виконайте збірку.

## Перший сеанс із власною програмою

На початку MiniDbg зупиняється на системній точці завантажувача.

Введіть:

```text
break entry
continue
regs
mem rip 16
step
regs
```

Це дозволить зупинитися на вході програми, переглянути стан процесора та виконати одну інструкцію.

`Entry point` не обов’язково є функцією `main`: зазвичай це початок коду запуску runtime.

`step` виконує машинну інструкцію, а не рядок C. Зміни регістрів після повторного `regs` позначаються символом `*`.

Через ASLR абсолютні адреси можуть змінюватися між запусками. Для точки всередині програми потрібна актуальна адреса початку інструкції.

## Демонстраційна програма

З кореня проєкту виконайте:

```powershell
.\bin\minidbg.exe .\bin\demo.exe
```

Сценарій демонстрації:

1. На початковій системній зупинці введіть `continue`.
2. Демо надрукує адреси `checkpoint` і `total`, а також готові команди `break` і `mem`.
3. Скопіюйте надруковану команду `break`.
4. Введіть `continue`. Очікується повідомлення `Hit breakpoint 1`.
5. Виконайте `regs` і команду `mem` із демо.
6. Виконайте `step`, потім `regs`, щоб побачити зміну RIP.
7. Продовжуйте виконання через `continue`, переглядаючи `total` між зупинками.

Перед трьома викликами `checkpoint` значення `total` становитиме 0, 1 і 3. Після завершення програма виведе:

```text
total = 6
```

Дебагер повідомить про завершення процесу з кодом 0.

Власний INT3 у демо потрібен для зручного показу адрес. Інші сумісні програми можуть запускатися без додавання INT3 до їхнього коду.

## Архітектура

| Файл | Відповідальність |
| --- | --- |
| `src/main.c` | Запуск процесу, цикл подій, потоки, винятки та Trap Flag. |
| `src/debugger.c` | Робота з точками зупинки та низькорівневий доступ до процесу. |
| `src/commands.c` | Розбір команд, перевірка аргументів і адресні псевдоніми. |
| `src/target.c` | Вибір програми, пошук файла та Unicode-шляхи. |
| `src/inspect.c` | Вивід регістрів і пам’яті. |
| `src/console.c` | Оформлення консолі та статистика сеансу. |
| `src/debugger.h` | Спільні структури, константи та інтерфейси. |

### Принцип роботи точки зупинки

1. MiniDbg зберігає початковий байт інструкції та записує `0xCC`.
2. Процес зупиняється на INT3.
3. Дебагер відновлює початковий байт і повертає RIP на адресу інструкції.
4. Через Trap Flag виконується одна інструкція.
5. Точка зупинки встановлюється повторно.

Захист сторінки після запису відновлюється, кеш інструкцій очищується через `FlushInstructionCache`.

Під час внутрішнього кроку інші потоки тимчасово призупиняються, щоб не пропустити зняту точку зупинки.

## Тестування

```powershell
.\build.ps1 -Test
```

Для вибору інтерпретатора:

```powershell
.\build.ps1 -Test -Python "C:\Path\python.exe"
```

До проєкту входять:

- модульні C-тести розбору команд;
- модульні C-тести доступу до пам’яті та роботи з байтами точок зупинки;
- 22 інтеграційні тести дебагера;
- 11 тестів вибору програми.

Перевіряються повторні й сусідні точки зупинки, відновлення RIP, кроки, регістри, пам’ять, захист сторінок, потоки, винятки, завершення, помилковий ввід, Unicode та порядок пошуку файлів.

Перевірено на Windows x64: збірка, модульні тести розбору команд і доступу до пам’яті та всі 33 інтеграційні тести пройдені. Два повідомлення Windows error 998 під час тестів пам’яті очікувані: перевіряється відмова запису за недоступними адресами.

## Обмеження

- Підтримуються native Windows x64-програми. Підтримка x86 та ARM64 не реалізована.
- Один цільовий процес; до 16 точок зупинки та до 64 відстежуваних потоків.
- Немає attach до вже запущеного процесу, налагодження дочірніх процесів і передачі аргументів цілі.
- Немає PDB, локальних змінних, прив’язки до рядків вихідного коду та дизасемблера.
- Адресу початку інструкції для точки зупинки обирає користувач.
- Видалення точок зупинки й апаратні точки не реалізовані.
- Крок через очікування іншого призупиненого потоку може спричинити зависання.
- Недоступні та guard-сторінки не розблоковуються для перегляду.
- `quit` на зупинці та кінець вводу завершують ціль із кодом 1.
- Налагодження захищених системних процесів не передбачено.
